## 1. 评审概览

### 1.1 评审方法

1. **双视角**：架构师视角负责技术可行性 / 边界条件 / 安全风险；产品经理视角负责需求完整性 / 用户体验。
2. **勾稽核对**：spec.md（需求基线 + AC-01~16 + 边界 5.1~5.9）↔ 三份设计文档 ↔ 原始需求文档 ↔ checklist.md 逐条比对；重点核对了 spec 第 5 节 5.1~5.9 与 api.md 2.1 边界映射表的覆盖度、spec 3.2 数据模型与 database-design.md 11 张表的字段一致性、architecture.md 决策 D1~D9 与 schema/api 的落地闭环。
3. **级别定义**：
   - **P0**：安全漏洞或核心业务闭环破坏，冻结前必须修订；
   - **P1**：文档间不一致、功能闭环缺口或可实现性缺口，冻结前应修订；
   - **P2**：可记录为已知限制、运维事项或纳入 v2 建议池。

### 1.2 总体评价

三份设计文档整体质量良好：模块划分与 spec 一一对应、52 个接口覆盖 spec 3.3~3.11 全量、错误码/鉴权/限流三张表完整、SQLite 适配决策（WAL/乐观锁/orders 表名/部分唯一索引）论证充分。主要问题集中在四类：**①状态联动的口径未闭环**（求购已成交、商品已售出、通知机制、会话已读）；**②若干安全边界未收紧**（非在售商品直连泄露为 P0）；**③两个技术点当前设计无法实现**（修改密码全量失效 Token、上传 fileHash 幂等无持久化）；**④SQLite 约束异常未定义到错误码的映射**。

## 3. 详细发现

> 每条含：编号 · 级别 · 涉及文档章节 · 问题描述 · 影响 · 建议处置。P0/P1 逐条展开，P2 以表格汇总。

### 3.1 维度一：需求完整性（遗漏功能点）— 4×P1, 5×P2

#### F1 · P1 通知机制缺失

- **位置**：spec.md 1.2 故事 8（"收到商品留言通知"）、2.3 接单步骤 2（"通知求购者"）、2.5 订单跟踪 ↔ api.md 全文（仅会话轮询，无任何通知接口）
- **问题**：spec 明确要求三类通知（留言通知、接单通知、订单流转知晓），但数据模型无通知表，API 无通知接口；接单"自动创建会话并通知求购者"中"通知"如何落地未定义。
- **影响**：AC-07（接单链路）中"通知求购者"无法验收；卖家不知道有人留言，核心互动体验断裂。
- **建议**：v1 最小方案二选一并写入 api.md 口径：①复用会话通道——留言/接单时向对方发送一条系统消息（sender 标注"系统"），零新增表；②明确砍掉通知，需求方确认。独立 `notification` 表 + `GET /notifications` 列入 v2。

#### F2 · P1 求购"已成交"状态无触发路径

- **位置**：database-design.md 3.5（want_buy.status 含'已成交'）↔ api.md 5.4（接单 #26 不改状态，无"标记成交"接口）
- **问题**：'已成交'枚举存在，但全部 52 个接口中没有任何路径能将求购置为已成交：接单不改状态，订单 confirmComplete 也未定义联动 want_id。
- **影响**：求购广场永远显示"进行中"的僵尸数据；状态枚举形同虚设。
- **建议**：api.md #37（confirmComplete）补充联动规则：订单关联 want_id 时，完成同时将 want_buy.status 置'已成交'；或新增求购者"标记成交"动作。

#### F3 · P1 商品"已售出"双路径冲突

- **位置**：api.md #15（PATCH /goods/{id}/status，action=markSold）与 #37（订单 confirmComplete 联动商品→已售出）
- **问题**："已售出"存在两个写入方（发布者手动 / 订单完成联动），二者与"进行中订单"的一致性矩阵未定义：先手动标记已售出后，既有"待沟通"订单再 confirmComplete 会怎样？有进行中订单时是否允许手动 markSold？
- **影响**：出现"商品已售出但订单还在待沟通"的矛盾状态；AC-09 与 AC-04 交叉场景无法判定。
- **建议**：api.md 2.1（边界 5.7 行）补充互斥规则，推荐：存在进行中订单（待沟通/待交易）时禁手动 markSold（409）；订单完成联动 markSold 已存在时幂等跳过。

#### F5 · P1 会话"已读"无接口

- **位置**：database-design.md 3.8（message.is_read 字段）↔ api.md 5.5（#30/#31/#32 无标记已读接口）
- **问题**：is_read 支撑未读数计算，但没有任何接口在用户查看会话后将消息置为已读——未读数只增不清零。
- **影响**：会话列表未读红点永久存在，AC-08 场景（会话列表含未读数）体验失效。
- **建议**：新增 `PATCH /conversations/{id}/read`（参与者权限，将该会话中对方发送的 is_read=0 批量置 1）；或约定 #31 拉取聊天记录时服务端自动置已读（更省一次请求）。任选其一写入 api.md 5.5。

### 3.2 维度二：边界条件（未处理异常）— 4×P1, 6×P2

#### F10 · P1 SQLite 约束异常会被映射为 500

- **位置**：sql/schema.sql（CHECK/FK/UNIQUE 约束）↔ architecture.md 1.2（GlobalExceptionHandler）↔ api.md 第 2 节错误码表
- **问题**：SQLite 违反 CHECK/UNIQUE/FK 时驱动抛 `SQLiteException`，若异常处理器只兜底 500，则所有本应 400/409 的场景（非法枚举、并发注册同学号、重复待处理举报触发 uk_report_pending）都变成"服务繁忙"。
- **影响**：直接破坏 AC-01（错误提示明确）、AC-06 及边界 5.1/5.8 的验收；排查困难。
- **建议**：GlobalExceptionHandler 增加对 SQLiteException 的分类翻译（按 message 前缀：UNIQUE constraint failed → 409；CHECK constraint failed → 400；FOREIGN KEY → 409），写入 api.md 第 2 节与 Task 4 验收。

#### F11 · P1 SQLITE_BUSY 超时行为未定义

- **位置**：architecture.md D2（busy_timeout=5000）
- **问题**：SQLite 单写者，发消息/下单/审核并发写超过 busy_timeout 时抛 SQLITE_BUSY，文档未定义该异常的用户表现与重试策略。
- **影响**：写高峰期用户看到 500；无重试约定导致前端行为不可预期。
- **建议**：Service 保持短事务（已在 D2 声明）；SQLITE_BUSY 捕获后同事务内重试 1 次，仍失败返回 409"操作冲突，请重试"；部署监控增加 busy 计数（写入 architecture.md 4.1 运维项）。

#### F12 · P1 goods 无并发保护（审核竞态）

- **位置**：database-design.md 3.4（goods 无 version）↔ 3.9（orders 有 version）↔ api.md #13 #42
- **问题**：订单有乐观锁而商品没有。两管理员同时审核同一商品（一通过一驳回）、管理员审核与卖家同时编辑，均为"读-改-写"竞态，互相覆盖。
- **影响**：审核结果不确定；AC-10 审核闭环在并发下不可靠。
- **建议**：goods 状态流转/审核一律用状态条件 UPDATE（`WHERE id=? AND status='待审核'`，或 UPDATE 带 updated_at 校验），影响行数=0 返回 409"状态已变更，请刷新"。写入 api.md #42 边界列与 database-design.md 3.4。

#### F13 · P1 举报目标已删除时处理动作 404 未定义

- **位置**：api.md #46（takeDownGoods/deleteComment 等联动动作）
- **问题**：举报的目标（商品/留言）可能在处理前已被发布者删除/逻辑删除，此时执行"下架商品/删除留言"目标不存在，行为未定义。
- **影响**：管理员处理举报时报错中断，举报永远无法关闭。
- **建议**：定义"目标已不存在 → 举报标记'已处理'，handle_result 记录'目标已被删除'"，api.md #46 边界列补充。

### 3.3 维度三：技术可行性（实现难点）— 2×P1, 5×P2

#### F20 · P1 "修改密码后旧 Token 全部失效"当前设计无法实现

- **位置**：api.md #6（"成功后旧 Token 全部失效"）↔ architecture.md D1（JWT 无状态 + Caffeine 黑名单只存登出的单枚 Token）↔ database-design.md 3.1（user 表无版本字段）
- **问题**：JWT 无状态校验下，让"该用户所有已签发 Token"失效需要服务端持有用户级失效水位；当前 user 表无 token_version，黑名单只按单 Token 记录，做不到全量失效。
- **影响**：api.md 契约承诺了一个实现不了的行为；或实现时悄悄降级（改密后旧 Token 仍有效 ≤2h），评审契约与实现不符。
- **建议**（二选一，冻结前定）：①user 表加 `token_version INTEGER DEFAULT 0`，JWT 载荷携带版本号，拦截器校验比对；改密/禁用时 +1（禁用场景现有"实时校验用户状态"已覆盖，可只处理改密）；②放宽 api.md #6 口径为"旧 Token 于剩余有效期内自然失效（≤2h）"。推荐 ①（成本低且语义完整）。

#### F21 · P1 上传幂等 fileHash 无持久化支撑

- **位置**：architecture.md D6（"按 fileHash 查重返回同一 URL"）↔ database-design.md（11 张表无文件记录表）
- **问题**：hash→URL 的映射需要持久化存储，11 张表里没有文件表，查重无处可查。
- **影响**：边界 5.9"同一文件重复上传返回同一 URL（幂等）"无法实现。
- **建议**（推荐前者，零表成本）：①**文件名=内容 MD5**（`uploads/yyyyMM/{md5}.{ext}`），同内容天然落同一路径，无需任何表，顺带去重存储；②新增 `file_record(hash UNIQUE, url, size, uploader_id, created_at)` 第 12 张表——需评审确认对 spec 3.2 的偏离。修改 D6 与 api.md #40 对齐。

### 3.4 维度四：安全风险 — 1×P0, 3×P1, 4×P2

#### F27 · P0 非在售商品可被 ID 直连访问（审核前内容泄露）

- **位置**：api.md #11（GET /goods/{id} 公开）↔ 鉴权矩阵 P0 层 ↔ api.md 2.1 边界 5.6（仅处理了"留言/私聊"侧）
- **问题**：商品详情为公开接口，对 status=待审核/已驳回/违规下架/已下架的商品无访问控制。未登录用户枚举 id 即可看到**尚未通过审核**的图文内容（含违规内容），审核流程被绕过；已下架/违规下架商品也不应对普通用户可见。
- **影响**：**安全漏洞**（信息泄露）+ 审核机制失效；AC-10/AC-14 相关场景存在缺口。这是本次评审唯一 P0。
- **建议**：GET /goods/{id} 规则收紧——status ∈ {在售, 已售出} 对外可见；其余状态仅发布者本人与管理员可见，他人返回 404（不泄露存在性）；公开列表接口恒只查 status=在售。修订 api.md #11 边界列 + 第 3 节鉴权矩阵（P0 层加注）。

#### F28 · P1 JWT 签名密钥管理缺失

- **位置**：architecture.md 3.1（jjwt 选型）——未定义密钥来源
- **问题**：若 secret 写在 application.yml 入库，密钥泄漏=任意伪造任意用户 Token，且无轮换手段。
- **影响**：认证体系被整体击穿的单点。
- **建议**：architecture.md 补一条安全约定：secret 经环境变量注入、长度 ≥256bit、不进代码仓库、明确轮换预案（轮换=全员重新登录，可接受）。

#### F29 · P1 上传仅扩展名/Content-Type 校验可被伪造

- **位置**：api.md #40（jpg/png/webp 校验）↔ spec 6.2（"上传文件校验类型与大小"）
- **问题**：客户端可把任意内容（HTML/脚本）改名为 .jpg 上传；若静态托管响应被浏览器嗅探执行，形成存储型攻击面。
- **影响**：绕过上传白名单，潜在 XSS/钓鱼托管。
- **建议**：服务端做魔数（magic bytes）校验（JPEG FF D8 FF / PNG 89 50 4E 47 / WebP RIFF....WEBP）；Nginx `/uploads/` 加 `X-Content-Type-Options: nosniff` 并固定 `default_type image/*`；写入 api.md #40 与部署章节。

#### F30 · P1 限流键取 IP 可被 X-Forwarded-For 伪造

- **位置**：api.md 第 4 节（登录按 IP+学号、注册按 IP 限流）
- **问题**：若应用直接读 X-Forwarded-For，攻击者可伪造头绕过 IP 限流；若直连读 RemoteAddr 又会全是 Nginx IP（误伤全体）。
- **影响**：注册/登录限流失效，防刷目标落空。
- **建议**：明确约定：应用仅信任 Nginx 注入的 `X-Real-IP`（Nginx 层设置 `proxy_set_header X-Real-IP $remote_addr`，并覆盖/剥离客户端携带的 XFF）；写入 api.md 第 4 节与部署配置。

### 3.5 维度五：用户体验 — 1×P1, 5×P2

#### F35 · P1 JWT 2h 有效期无刷新机制

- **位置**：api.md 第 1 节（有效期 2h）↔ spec 6.3（可用性）
- **问题**：2h 后所有登录态突然失效，用户在发布图文/聊天中途被强制登出且无预兆；H5 场景重登成本高。
- **影响**：核心写操作流程中断，发布/聊天完成率下降；spec 6.3"可用性 ≥99.5%"体验目标打折。
- **建议**：采用滑动续期——拦截器发现 Token 剩余有效期 <30min 时，在响应头返回新 Token（`X-New-Token`），前端无感替换；或引入 refresh token。与 F20 的 token_version 方案合并实现。写入 api.md 第 1 节约定。
